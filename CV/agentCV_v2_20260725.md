（第三行建议用小一号字体或灰色，视觉上从属于学历行，不要抢主体信息的位置）

**为什么必须把"毕业证书时间"和"可入职时间"分开写**（这是海外硕士在国内求职最常见的一个坑）：

- 你的**课程和论文 2026 年 9 月前就结束了**，但学位证书要等到 **11 月底**才发。
- 如果简历上只写"2026.11 毕业",HR 的默认理解是"**12 月才能来上班**"——很多岗位会因为入职时间太晚直接过滤掉你,而这跟事实不符。
- 反过来只写 2026.09 也不行:入职时 HR 要查毕业证,时间对不上会被认为**简历造假**,这个后果比被过滤严重得多。
- **正解是两个时间都给**：证书时间写真实的 2026.11，另外明确标注你实际能到岗的时间。绝大多数公司接受用**成绩单 + 课程完成证明（Completion Letter）**先办入职，证书后补。

**可入职 2026.09.01 是个有竞争力的时间**——比多数海外硕士能给的都早（很多人写 10 月甚至次年 1 月）。既然能给这么早，就一定要写出来，否则 HR 只看到 2026.11 会默认你 12 月才到岗。

**被 HR 追问时怎么答（准备好这两句）**：

- 问"11 月才毕业怎么 9 月入职？"→ "我的课程和毕业论文 8 月就全部完成了，9 月起可以全职工作。学位证书是学校统一 11 月发放，入职时我可以提供**成绩单和课程完成证明（Completion Letter）**，证书 11 月拿到后补交。"
- 问"学历认证什么时候能办？"→ 实话说：**中留服学历认证需要凭学位证书办理**，所以认证会在 11 月拿证之后。绝大多数公司对应届生接受**先签承诺书、后补认证**，但如果某家公司明确要求入职前完成认证，那就是硬门槛，提前问清楚比入职后卡住好。

**另外这件事影响"届别"判定**：`docs/ideas/job-track-priority.md` 里本来就挂着一条待验证假设——"提前批对 2026.09 海外毕业生开放，部分公司按 2027 届算，需逐家确认"。**证书日期变成 2026.11 之后，你被算作 2027 届的可能性明显变大**，而你现在投的恰好就是 2027 届提前批,这个方向上其实是**有利的**。但投递前务必逐家看 JD 的届别定义（通常写在"招聘对象"一栏，按毕业证日期算）。

## 三、工作内容（6 条，替换原 5 条）

- **设计分层架构**：数据导入层（CSV → SQLite benchmark 数据库）、指标层（speedup / parallel efficiency 计算）、工具层（最优配置查询、模式对比、扩展性报告等确定性分析工具）、路由层（中文意图识别 + LLM function calling 双实现）与 CLI 层，各层输入输出合同由 **121 项自动化测试**钉死，全量测试离线可跑。

- **实现中文规则 router**：关键词意图分类 + 问题规模解析（阿拉伯数字、"100 万"混写、中文数字"一百万"），缺参数时主动追问、超范围问题明确拒答；**路由输出与 LLM tool call 严格同构（intent + 参数）**，使两种 router 可用同一评测集打分、且切换只需改一行 dispatch。

- **封装确定性分析工具**：单规模最优配置查询、MPI-only 与 hybrid 模式对比（数据只含 ranks/threads，故采用保守标签 mpi_like / hybrid_like）、扩展性报告生成；同一数据库生成的 Markdown 报告**字节级一致**（刻意不含时间戳），使"文档是否漂移"退化为一次 git diff 检查。

- **基于真实 ARCHER2 数据验证**：100 万未知数规模下单核 245.7s → 128 核 3.866s（speedup 63.6、并行效率 49.7%），识别出 2/4 核超线性加速（cache 效应，效率 147% / 126%）与 32 核 hybrid 配置的效率坍缩（0.33），并由规则自动生成中文解读段落。

- **接入 LLM function calling router**：定义 tool schema（description 写明工具边界、`unknowns` 参数刻意可选——模型省略参数即表达"追问"、不调用任何工具即表达"拒答"）;实现**防御式响应解析**,将模型未调用工具、调用不存在的工具、arguments 非合法 JSON 三类异常统一收敛为显式 unknown,**绝不猜测参数以避免"静默算错"**；API 失败选择向上抛出而非回退规则 router，以防污染评测。全部单元测试通过 **FakeLLM 依赖注入**离线运行，不需要 API key。

- **建立评测机制与对比结论**：自建 **30 问五类中文评测集**（正常题 / 追问题 / 拒答题 / 数字陷阱题 / **规则已知会错的对抗题**），期望值为 tool call 而非答案文本；评测 harness 接受任意 router 函数、对实现完全无知。结果：**规则 router 83.3%（对抗题 0/4）、LLM router 100%**；**消融实验显示同一模型不加 system prompt 仅 63.3%**，说明 function calling 的准确率主要由工具说明书与策略 prompt 决定。评测报告中如实标注局限（题量、单模型单次运行、prompt 在测试集上调优的乐观偏差）。

- **工程纪律**：pytest 全量离线可跑、不依赖 API key（key 走环境变量，永不入库）；README demo 命令逐条可复现；**以"公开声称 == 已实现功能"作为文档与简历的验收约束**。
