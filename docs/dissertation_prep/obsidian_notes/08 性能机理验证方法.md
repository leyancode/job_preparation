# 性能机理验证方法

## 读前概念

| 术语 | 含义 |
| --- | --- |
| observation | 实验直接测到的事实，例如某布局的Eq/s更高 |
| correlation | 两个量一起变化，但尚未证明一个造成另一个 |
| causation | 改变一个因素会导致另一个结果发生可重复变化 |
| hypothesis | 对原因提出的、可以被实验检验的解释 |
| prediction | 如果hypothesis成立，应当观察到的具体结果 |
| control variable | 实验中保持不变的条件，例如问题规模、节点数和binary |
| intervention | 主动改变一个候选原因，例如只改变线程绑定方式 |
| alternative explanation | 同样能够解释现象的其他原因 |

机理验证的目标不是给性能差异配一个听起来合理的硬件故事，而是让假设产生可测预测，再用控制实验区分竞争解释。

## 一、从性能相关性走向机理证据

当前实验已经证明：布局改变时性能排序也改变。机理验证需要更长的证据链：

```text
候选机制
  ↓ 提出可观察预测
拓扑/软件结构证据
  ↓
profiling指标按预测变化
  ↓
控制变量干预后性能按预测变化
  ↓
排除主要替代解释
```

例如“16×8跨两个CCX，所以更慢”只是候选解释。更完整的验证应包含：

1. `xthi`确认16×8确实跨两个CCX；
2. MAP显示它有更高缓存/内存或OpenMP同步成本；
3. `-log_view`显示差异不只是迭代数造成；
4. 改变close/spread或rank placement后，指标与性能按预测方向变化；
5. 同一现象在多个代表点复现。

## 二、四类候选机制

### 机制A：CCX/L3局部性

假设：4-thread rank可以局限在一个CCX；8-thread rank跨两个CCX，降低L3局部性。

预测：

- 16×8的memory time或cache-related指标更差；
- 线程间负载正常，但每次MatMult/PCApply时间上升；
- 改变线程放置会明显改变性能；
- 同一布局中，跨CCX的放置比CCX内放置慢。

需要证据：xthi、MAP memory/cache指标、per-event time/iteration、controlled affinity experiment。

### 机制B：NUMA与first-touch

假设：初始化和计算线程的NUMA归属不一致，造成远程内存访问。

预测：

- 远程NUMA流量或memory time增加；
- thread placement变化后结果明显变化；
- 性能差异集中在内存密集的MatMult/PCApply。

> [!warning]- 不要把跨CCX写成跨NUMA
> 8-thread rank通常仍位于同一个16-core NUMA region。只有实际affinity跨过16-core边界时，才适合提出NUMA解释。

### 机制C：MPI通信端点与等待

假设：hybrid布局减少MPI ranks，从而减少消息、通信端点或global reduction参与者。

预测：

- ranks减少后messages/iteration或VecScatter成本下降；
- reductions数量可能不变，但归约参与进程数减少；
- 高节点数时hybrid相对flat MPI的优势扩大；
- MAP中MPI wait或imbalance发生对应变化。

### 机制D：OpenMP覆盖与同步

假设：更多threads/rank带来同步、调度或负载不均衡，超过通信减少的收益。

预测：

- 16×8比32×4出现更多OpenMP synchronization或worker idle；
- MPI时间可能下降，但总时间上升；
- 主要热点没有足够threaded work，worker activity不足；
- 线程数增加后MatMult或PCApply没有按比例加速。

## 三、三阶段验证计划

### 阶段1：拓扑事实，成本很低

在一个完整节点上对四个布局运行 `xthi`：

```text
128×1, 64×2, 32×4, 16×8
```

保存：

- job ID与node ID；
- module和编译环境；
- 每个rank/thread的CPU affinity；
- CPU到CCX、NUMA、socket的映射；
- 实际threads/rank和是否使用SMT。

### 阶段2：利用现有数据，不提交新任务

从正式 `-log_view` 日志生成event-level表：

```text
dimension, scale, nodes, layout,
iterations,
MatMult_time_per_iteration,
PCApply_time_per_iteration,
VecScatterEnd_time_per_iteration,
messages_per_iteration,
bytes_per_iteration,
reductions_per_iteration
```

从现有MAP campaign比较32×4与16×8：

- MPI time；
- OpenMP worker activity；
- synchronization；
- memory operations；
- process imbalance。

只比较同一MAP campaign。正式scaling时间继续来自uninstrumented runs。

### 阶段3：控制变量实验

选1–2个差异明显且成本可接受的点：

- 固定dimension、scale、nodes、layout、binary、solver；
- 只改变 `OMP_PROC_BIND=close/spread` 或明确的rank placement；
- 每种条件做5–10次交错重复；
- 每次都用xthi或CPU mask确认实际放置；
- 比较Eq/s、seconds/iteration和event-level指标。

如果目的是解释64×2为什么在2D中最好，需要采集64×2的定向profile。现有baseline MAP不包含该布局。

## 四、代表点怎样选择

| 目的 | 选择原则 |
| --- | --- |
| 解释最大收益 | 选择largest point，如165m/32 nodes |
| 控制profiling成本 | 先用20m或41m的中等节点点pilot |
| 比较32×4与16×8 | 选择两者差距大的点 |
| 检验接近排序 | 选择observed ranges重叠的点并增加重复 |
| 分析强扩展变化 | 选择同一scale相邻两个node counts |

不要因为某点“看起来有趣”就选择。把规则写入分析记录，使选择可以复现。

## 五、替代解释检查表

> [!warning]- 每次归因前检查
> - 是否只是KSP iterations不同？  
> - 是否混入了PCSetUp或Main Stage？  
> - 是否把MAP时间与uninstrumented时间比较？  
> - 是否有不同PETSc arch或错误LibSci链接？  
> - 实际rank/thread count是否正确？  
> - affinity是否重叠或使用SMT？  
> - 三次运行波动是否与布局差异同量级？  
> - 2D/3D每个equation的工作量是否不同？  
> - 当前连续行分区是否支持所声称的几何通信模型？

## 六、结论措辞等级

| 证据 | 推荐措辞 |
| --- | --- |
| 只有性能排序 | “与该机制一致” |
| 有affinity和profiling相关性 | “支持该机制作为解释” |
| 有控制干预并跨点复现 | “提供较强的机理证据” |
| 没有排除替代解释 | 不使用“由……导致” |

## 一句话总结

拓扑告诉我们程序运行在哪里，profiling告诉我们时间花在哪里，控制实验才开始回答为什么。

## 自测

> [!example]- 为什么“32×4更快”不能证明CCX/L3是原因？
> 排序只给出相关性。还需要确认实际放置、观察cache或runtime指标，并通过只改变放置的实验检验预测。

> [!example]- 什么是控制变量实验？
> 固定dimension、scale、nodes、layout、binary和solver，只改变一个候选原因，例如 `OMP_PROC_BIND`，再比较结果。

> [!example]- 哪些现象会成为CCX假设的替代解释？
> KSP迭代数变化、MPI消息变化、OpenMP同步、NUMA远程访问和系统噪声都可能产生相似排序。
