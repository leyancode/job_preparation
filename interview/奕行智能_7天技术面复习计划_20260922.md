## 2. 各天详细范围（正文按这个补）

### Day 1 · Transformer 推理原理与算子清单

- **结构**：embedding → N × [RMSNorm → QKV projection → RoPE → Attention → O projection → 残差 → RMSNorm → FFN(SwiGLU: gate/up/down) → 残差] → final norm → lm_head。
- **Attention 数学**：`softmax(QKᵀ/√d)V`；因果 mask；MHA / GQA / MQA 的区别与 KV cache 大小的关系。
- **KV cache**：为什么需要、大小公式 `2 × L × n_kv_heads × d_head × seq × batch × bytes`；用 Llama-3-8B、Qwen 系列算一个实数。
- **Prefill vs decode**：prefill 是大 GEMM（compute-bound），decode 是 GEMV（memory-bound，每 token 读一遍全部权重）；算术强度公式 `FLOPs / bytes`；批大小怎么把 decode 推向 compute-bound。
- **每 token FLOPs ≈ 2 × 参数量**；每 token bytes ≈ 权重字节数 + KV cache 读写；用它推 `tokens/s 上限 = 带宽 / 每 token 字节数`。
- **MoE**：router（top-k）、专家并行、激活参数 vs 总参数、负载不均与容量因子。
- **动手**：用 PyTorch 在 CPU 上加载一个小模型（或手写一个 2 层 toy transformer），`torch.profiler` 看算子时间分布，验证 decode 阶段 linear 占主导。
- **10 问示例**：为什么 decode 慢在带宽不在算力；GQA 为什么省显存又几乎不掉精度；KV cache 为什么不能无限长；RoPE 是什么、为什么外推有问题；MoE 为什么算力便宜但通信贵。

### Day 2 · 核心算子性能

- **GEMM**：`M×K · K×N`，FLOPs = 2MNK；算术强度随分块尺寸增长（`2MNK / (2·(MK + KN + MN))`）；tiling 分层（寄存器 / 片上 SRAM / 片外 HBM）；MFU = 实测 FLOP/s ÷ 峰值；形状不好（K 小、N 不整除阵列宽度）为什么利用率低；GEMV（decode）为什么注定低 MFU。
- **Attention**：朴素实现 O(seq²) 中间矩阵要写回内存；**FlashAttention** 的核心 = 分块 + online softmax（不物化 S 矩阵）；decode 阶段的 attention 是读 KV cache 的带宽问题；PagedAttention 解决的是 KV cache 内存碎片而非算力。
- **Softmax / Norm / 激活 / 残差**：元素级、访存受限；**算子融合**（norm + linear、gate·up·silu、attention 内部）减少往返片外内存的次数——这是 NPU 上最常见的优化。
- **MoE**：expert 计算是很多小 GEMM；专家负载不均 → 部分核空转（和你的 OpenMP 空转是同一类现象）；all-to-all 通信；capacity / drop / padding 的取舍。
- **性能工具词汇**：MFU / HFU、带宽利用率、算子 launch 开销、DMA 与计算的重叠、pipeline bubble、tail effect。
- **动手**：numpy 写分块 GEMM 对比朴素实现；写 online softmax 验证与朴素 softmax 等价。
- **10 问示例**：怎么判断一个 GEMM 是 compute-bound 还是 memory-bound；FlashAttention 为什么快（不是减少 FLOPs）；算子融合的收益从哪来；MoE 为什么在小 batch 下利用率差。

### Day 3 · 数据类型与量化 · 精度问题定位

- **格式**：FP32 / TF32 / FP16（5 位指数，易溢出）/ BF16（8 位指数，精度低但范围同 FP32）/ FP8 E4M3 & E5M2 / INT8 / INT4；累加精度（INT8 乘 → INT32 累加，FP16 乘 → FP32 累加）为什么重要。
- **量化**：对称 / 非对称、scale & zero-point、per-tensor / per-channel / per-group（group=128）；**weight-only**（GPTQ、AWQ，解决 decode 带宽）vs **W8A8**（SmoothQuant，激活离群值迁移到权重）；KV cache 量化；PTQ 流程（校准集 → 统计 → 量化 → 评估）vs QAT。
- **精度评估**：perplexity、下游任务、逐层输出与 golden 的余弦相似度 / 相对误差；哪些层敏感（首尾层、attention 的 softmax 前后、norm）。
- **精度问题定位流程**：固定随机性 → 单算子对拍 → 二分定位层 → 检查离群值 / 溢出 / 累加精度 / 舍入模式 / 算子实现差异（如 GeLU 近似式）。
- **对芯片性能的影响**：低比特 → 每 token 字节数下降 → decode 直接提速；INT8 阵列吞吐通常 2× FP16；但反量化开销与不支持的格式会吃掉收益。
- **动手**：用 numpy 手写 per-channel 对称 INT8 量化 + 反量化，测一个随机矩阵的相对误差；用 `torch.ao.quantization` 或手写对一个 linear 层做 PTQ。
- **10 问示例**：BF16 和 FP16 选哪个、为什么；为什么 weight-only 量化在 decode 有效在 prefill 没用；SmoothQuant 解决什么；量化后精度掉了，第一步查什么；per-group 为什么比 per-channel 精度好、代价是什么。

### Day 4 · AI 加速器体系结构

- **GPU 复习（课程层级）**：SM / warp / tensor core、寄存器–shared–L2–HBM、occupancy、访存合并、kernel launch。
- **NPU / TPU 类架构**（奕行是「类 TPU」）：脉动阵列（systolic array）原理、MAC 阵列尺寸与 GEMM 形状匹配、**显式管理的片上 SRAM（scratchpad，不是 cache）**、DMA 显式搬运与**双缓冲**、数据流（weight-stationary / output-stationary / row-stationary）、tiling 由编译器静态决定、VLIW / 静态指令调度、向量单元处理 norm / softmax 等非 GEMM 算子、多核 + NoC 的切分（按 batch / 按 head / 按层）。
- **RISC-V + RVV**：可变向量长度（VLEN、`vsetvli`、LMUL）、为什么向量扩展适合做 AI 芯片的标量/向量侧、自研虚拟指令集（VISA 类）的作用 = 把编译器目标与硬件代际解耦。
- **对照表**：CPU（你的 EPYC 经验）/ GPU / NPU 在「谁管调度、谁管缓存、并行粒度、适合的算子」四个维度上的差异。
- **「一个 GEMM 在 NPU 上的生命周期」**：权重从 HBM → DMA → SRAM tile → 阵列 → 累加器 → 向量单元后处理 → 写回；哪一步会成为瓶颈、profiling 看什么计数器。
- **多芯片**：张量并行的 all-reduce、互联带宽为什么是宣传点。
- **动手**：手算一个 8B 模型 decode 在「某带宽 / 某算力」芯片上的 roofline 上限；画出 tiling 与双缓冲的时序图。
- **10 问示例**：脉动阵列为什么高效、什么形状跑不满；scratchpad 和 cache 的区别对软件意味着什么；数据流选择怎么影响片外访存；NoC 拥塞怎么表现；RVV 和 AVX 的根本区别。

### Day 5 · 部署与软件栈

- **PyTorch 工具链**：eager vs `torch.compile`（TorchDynamo / Inductor）、FX graph、`torch.profiler` / Chrome trace、forward hook 逐层抓输出、自定义算子注册与 fallback、ONNX 导出与算子集版本。
- **图编译与运行时**：算子融合、常量折叠、layout 转换（NCHW/NHWC）、静态 shape vs 动态 shape、TVM / MLIR 的位置；芯片厂商 SDK 的典型结构（前端 → 图优化 → 算子库 → 运行时驱动）。
- **推理引擎**：vLLM（PagedAttention、continuous batching）、TensorRT-LLM、llama.cpp（GGUF、CPU 后端）；**指标**：TTFT、TPOT / ITL、吞吐（tokens/s）、并发、延迟-吞吐曲线、batch size 拐点。
- **并行策略**：TP / PP / DP / EP / SP 各切什么、通信模式（all-reduce / P2P / all-to-all）、什么模型规模用什么。
- **推理优化清单**：KV cache 量化、投机解码、prefix caching、chunked prefill、算子融合、CUDA/NPU graph 消 launch 开销。
- **客户模型适配流程**：拿到模型 → 算子覆盖检查 → 不支持算子的三条路（分解 / 自定义 / CPU fallback）→ 精度对拍 → 性能基线 → 优化 → 回归测试自动化。
- **自动化测试**：golden 对比 + tolerance、pytest 参数化覆盖形状 / dtype、性能回归阈值——直接用你 HPC_Agent / benchmark 的 CI 经验讲。
- **可选动手（决定权在你）**：本机 llama.cpp 跑一个 1–2B Q4 模型的 `llama-bench`，记录 tokens/s，对照本机内存带宽算利用率——有一个**真实数字**在手，Day 7 讲「推理性能测试经验」时不空。
- **10 问示例**：TTFT 和 TPOT 分别由什么决定；continuous batching 解决什么；一个算子芯片不支持怎么办；怎么设计一个推理性能回归测试；TP 为什么需要高互联带宽。

### Day 6 · 问题定位方法论 + 手写题

- **固定流程**（背下来）：复现与固定变量（seed、shape、dtype、batch）→ 分层二分（模型 → 图 → 算子 → 指令）→ 三分归因：**模型**（结构 / 精度敏感层 / 动态 shape）、**软件栈**（算子实现、融合规则、layout、驱动版本、编译器 tiling 决策）、**硬件**（带宽、SRAM 容量、阵列形状、NoC、时钟 / 功耗墙）→ 用计数器证明而不是猜（对应你论文里「paid as」的纪律）。
- **6 个案例走一遍**：① decode tokens/s 只有理论上限 30% ② prefill 利用率低 ③ 量化后某任务精度崩 ④ MoE 模型吞吐随 batch 不涨 ⑤ 客户模型某算子结果与 PyTorch 不一致 ⑥ 多卡 TP 加速比差。
- **手写题**：数值稳定 softmax；单头 causal attention（numpy）；带 KV cache 的 decode 循环；分块 GEMM；per-channel INT8 量化 / 反量化；roofline 估算（给带宽、算力、模型大小求 tokens/s 上限与拐点 batch）；`torch.profiler` 用法；用 hook 逐层对拍的脚本。
- 顺带复习 Python 基础题：复杂度、生成器、pandas 聚合、pytest fixture / parametrize。
