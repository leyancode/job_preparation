### 1.2 驱动程序改了什么（`src/ex2_repeat.c`）

- 基于 PETSc 官方 `ex2.c`（2D five-point），加 `-num_solves <n>`（`PetscOptionsGetInt` + `PetscCheck(nsolves >= 1)`）。
- 第 1 次 `KSPSolve` 是 warm-up，付 `PCSetUp`（建 GAMG 层次）；然后 `PetscLogStageRegister("RepeatedSolves")` → `PetscLogStagePush` → 循环 `s = 1..nsolves-1` 共 19 次 → `PetscLogStagePop`。
- **每次 solve 前把解向量清零**，保证每次都跑完整迭代数（否则第二次起初值已是解，0 次迭代）。
- 运行时加 `-ksp_reuse_preconditioner -pc_gamg_reuse_interpolation true`，让 19 次复用 preconditioner；审计里「timed stage 无 PCSetUp」就是验证这一点。
- `3d_repeat.c`：自写 seven-point stencil（`-m -n -p`），同样的 warm-up / RepeatedSolves 约定。
- 构建：`--with-debugging=0 -O3 --with-openmp=1 --with-openmp-kernels=1 --with-blaslapack-lib=<LibSci threaded>`，Cray 包装器 `cc/CC/ftn`，`PETSC_ARCH=arch-omp-libsci-rome-opt`。128×1 是**同一个 OpenMP 构建**下的 flat MPI，隔离掉编译器 / 库差异。

### 1.3 提交脚本的两层设计

**提交器 `2Dlib_srun.sh`**（在登录节点跑）：
- `set -euo pipefail`；`ARCHER2_ACCOUNT="${ARCHER2_ACCOUNT:?...}"` 缺变量直接失败。
- 读规模表 CSV（scale, m, n, unknowns），对每个 nodes 用**准入窗口** `25k ≤ unknowns/core ≤ 100k` 过滤 → 自动生成两条 weak-scaling 链，不用手写矩阵。
- 对每个 threads ∈ {1,2,4,8}：`ppn = 128/threads`，`ntasks = nodes*ppn`，`sbatch --nodes --ntasks --ntasks-per-node --cpus-per-task --exclusive --export=ALL,SCALE=..,PPN=..,THREADS=..,REPEAT=3,NUM_SOLVES=20`。
- 全部参数可环境变量覆盖（`SCALES / NODES_LIST / THREADS_LIST / REPEAT / TIME_LIMIT`），pilot 与正式共用一个脚本。

**作业脚本 `2dlib_srun.sbatch`**（计算节点跑）：
- `module restore; module swap PrgEnv-cray PrgEnv-gnu/8.4.0; module unload cray-libsci`——环境显式声明。
- `OMP_NUM_THREADS / OMP_PLACES=cores / OMP_PROC_BIND=close / OMP_DYNAMIC=FALSE / SRUN_CPUS_PER_TASK`。
- `srun --ntasks --ntasks-per-node --cpus-per-task --exact --hint=nomultithread --distribution=block:block --cpu-bind=cores`。
- **3 次重复在同一个 job 内串行**，输出文件名编码全部元数据：`ex2_<arch>_<scale>_nodes<N>_ppn<P>_t<T>_job<ID>_rep<r>.log`；`| tee` 到按 `scale/nodesN/logs/` 分层的目录。
- `-log_view -ksp_converged_reason` 是分析的输入；`< /dev/null` 防止 srun 吃 stdin。

**Q 为什么三次重复放同一个 job？** 同一批节点、同一时间窗，减少机器状态漂移；`classify_run_sets` 也据此判定 reps == {1,2,3} 为 formal、{1} 为 pilot，其他一律报错。
**Q 为什么用 bash 不用 Python / Snakemake？** 登录节点上最稳的是 bash + sbatch；逻辑够简单（两层、一个循环）；复杂度真正在分析侧，那边全是 Python + pytest。若规模再大会考虑 workflow manager。

### 1.4 fake-Slurm 测试（`scripts/ksp/2d/tests/test_2dlib_srun.sh`）— 面试官最可能问「怎么在没有超算的 CI 上测提交脚本」

1. 静态检查：规模表每行 `m*n == unknowns`；作业脚本里**不能出现** `map` / `forge`（保证 scaling job 未插桩）；不能出现 `make / ldd / readelf`（提交时不构建）；必须含 `srun --ntasks="${NPROC}"`。
2. 动态检查：`mktemp -d`，写一个假 `sbatch`（只把参数 append 到 `SUBMISSION_LOG`），`PATH` 前置注入；跑提交器：
   - pilot `SCALES=20m NODES_LIST="2 4"` → 断言恰好 **8** 个 job；
   - 全量 6 规模 × 6 节点 → 准入窗口过滤后恰好 **44** 个 job（= 11 个 size/node 点 × 4 布局）；
   - grep 四种 `--ntasks-per-node` 都出现。
3. CI (`ci.yml`) 一个 job：`pytest -m "not private_evidence"` + 三个 bash 测试；`actions/checkout@v7`、Python 3.10、10 分钟超时。

### 1.5 分析入口的审计（`analysis/scripts/nproc_2d_libsci/analyze_repeated_fullnode_logs.py`）

`parse_log()` 对**每一份**日志：
- 文件名必须匹配正则，否则 `ValueError`；scale 必须在规模表里。
- 全文扫 `FAILURE_MARKERS`：`DIVERGED / PETSC ERROR / MPI_ABORT / CRAYBLAS_WARNING / Waiting for licence / srun: error / slurmstepd: error`。
- 正则抽 PETSc 自报字段：header `on a <arch> named <node> with <procs> process`、`Using N OpenMP threads`、`Norm of error … iterations … solves …`、`Time (sec)`、`--with-blaslapack-lib=`。
- `parse_repeated_stage()` 只读 `RepeatedSolves` stage：KSPSolve 计数与时间、PCSetUp 计数。
- **13 个布尔检查**（简历上归为六类：架构、ranks×threads、收敛、timed-stage 事件数、链接库、solver signature）：

| 检查 | 断言 |
|---|---|
| filename arch / reported arch | 都等于 `arch-omp-libsci-rome-opt` |
| full-node layout | `ppn × threads == 128` |
| **MPI processes** | header 自报 procs == nodes × ppn（← 302/303 就是这条抓的） |
| OpenMP threads | 自报 == 文件名 |
| driver solves / converged solves | 都 == 20 |
| timed solves | RepeatedSolves 里 KSPSolve == 19 |
| no repeated PCSetUp | stage 内 PCSetUp == 0 |
| positive total / repeated time | > 0 |
| unknowns/core window | 25k–100k |
| configured LibSci | 等于目标 `libsci_gnu_mp.so.5.0` 路径 |

任一失败 → 抛错、不进聚合。派生指标：`seconds_per_solve = t/19`、`seconds_per_iteration = t/(19·iters)`、`equations_per_sec = unknowns·19/t`。
之后 `validate_matrix()` 检查 44 个配置齐全，`summarize_formal_runs()` 取中位数 + min–max，`assign_upc_band()` 按 ~40k / ~80k（±15%）分链作图。
绘图：Okabe–Ito 色盲安全色、`MPLCONFIGDIR` 指向临时目录（CI 无 HOME 写权限也能跑）、`matplotlib.use("Agg")`。

- **Q 原始日志不公开，怎么让人信？** 44 行 + 24 行 summary、16 个脚本、5 份脱敏日志 + 双 SHA-256、审计逻辑本身开源可读；私有 workspace 才能全量重跑，这一点在 README `Limitations` 明写。

## 2. HPC_Agent — 工程细节

### 2.1 架构：六层 + 两个进程边界，依赖严格向下无环

```
L0  db.py（唯一的数据进出口，SQL 只在 db.py 与 metrics.py）· tracing.py（横切，不依赖任何业务模块）· llm_config.py · llm_schema.py
L1  importer.py（CSV→SQLite）· metrics.py（speedup / efficiency / scaling_summary）· tools.py（best_config / compare_modes）· rag.py
L2  router.py（规则路由 + ask 编排 + select_router）· llm_router.py（lazy import）· report.py
L3  cli.py  ⇄ 平级、互不依赖 ⇄  api.py（FastAPI 薄封装）
```

两条 **lazy import** 边是关键：`router.py` 只在 `select_router()` 的 `if name == 'llm'` 分支里 import `llm_router`；`llm_router.py` 只在 `_default_client()` 里 import `openai`。
→ 规则路径永远不加载 SDK，这就是 `pytest` 在无 key 环境全绿的根因。

### 2.2 一次 `ask` 的链路（能画出来）

`cli.py` 解析参数、**构造 Tracer 与 RAG context**（ask 不碰文件路径）→ `router.ask()` emit `ask_start` → `select_router()` **返回一个 callable**（规则 = `route` 本身，LLM = 绑定了 client 的闭包）→ 两者都返回同构 `{"intent", "unknowns"}` → emit `route_result` → 工具经 `traced()` 包装调用（tools.py 不知道 tracing 存在）→ `db.find_fastest_run()` → `{"found": bool, …}` → 只在 `ask()` 末尾的 f-string 渲染中文答案。

三个早返回：`intent == unknown` → 不支持；intent 合法但 `unknowns is None` → **追问不猜**；工具 `found: False` → 直接返回工具的 message。
**错误不降级**：LLM 路径失败（无 key / 网络 / 限流）异常向上抛，`ask()` 绝不静默退回规则 router；只有 `cli.py` 捕获 `LLMConfigError` 转成可读信息 + 退出码 2。
（注意：`SPEC.md` 里有一句旧的「LLM router degrades to rule router offline」，与 WORKFLOW/实现不一致——被问到就说实现是「不降级」，SPEC 那句是早期设想未更新。）

### 2.3 LLM function calling 的设计点

- **Tool schema**（`llm_schema.py`）：description 写的是**边界**（「仅当用户询问…时使用」），因为 description 在相邻工具之间做仲裁；`unknowns` 刻意**不在 `required`** 里——模型省略参数 = 追问信号。`intent_from_tool_call` 对不在集合内的工具名返回 unknown。
- **防御式解析**（`_parse_response`）：只读第一个 tool call；三类异常统一 → `{"intent":"unknown","unknowns":None}`：① 没调工具（tool_calls 为 None 或 []）② arguments 不是合法 JSON ③ 幻觉工具名。基础设施错误（网络等）**照常抛出**，不与路由决策混淆。
- **System prompt 三条策略**：意图明确但缺规模 → 仍调工具、省略参数；`unknowns` 是问题规模不是核数 / 迭代数 / job id；只做两件事。消融去掉它 → 100% 掉到 63.3%（11 题错：ask_back 0/5、parse_trap 0/4、歧义句 2/4）。

### 2.4 评测（`evals/`）

- `questions.jsonl` 30 题五类：normal / ask_back / reject / parse_trap（数字陷阱）/ rule_wrong（对抗）；期望值是 **tool call（intent + unknowns）而非答案文本**，两者都对才得分。
- 规则 router 5 个失败各有一行归因：job id 被当规模（#25）、`openmpi` 子串含 `mpi` 误触发（#27）、别名「混合」不在词表（#28）、「对比」抢先触发分支（#29）、「两千五百万」组合错且**静默返回错值**（#30，最危险）。
- 结论：LLM 分数几乎由 prompt 决定（36.7 点差 > 规则 vs LLM 的 16.7 点差）；「接上 function calling」不是能力，工具说明书和策略 prompt 才是。
- 局限主动说：30 题、出题人 = 作者、单模型（qwen3.7-plus）、temperature 0 单次运行——规则 router 的分是字节可复现的，LLM 的分是带元数据的一次测量。

### 2.5 测试策略（229 passed，16 个测试文件）

- 分布：`test_router` 43、`test_rag` 40、`test_tracing` 25、`test_api` 24、`test_llm_schema` 19、`test_llm_router` 14、`test_run_eval` 14、`test_report` 13、`test_cli` 9…
- 测试是**验收合同**：工具层按 key 逐项精确断言 dict；渲染层只断言必须出现的信息，措辞可改；`SPEC.md` 规定「实现不许改测试来通过」。
- LLM 路径用 `tests/fakes.py` 的 **FakeLLM 依赖注入**（client 参数），无网络无 key。
- 专门的**回归测试**：换 router 不改答案措辞；不开 `--rag` 时发给模型的 messages 与评测时**逐字节一致**；脱敏由一个扫描测试强制（绝对路径 → basename，key 类字段 → `[redacted]`）。
- `evals/run_eval.py` 自身也有测试（mock LLM）。

### 2.6 CI（`.github/workflows/ci.yml`）— 「公开声明 == 实现」的执行者

Job 1 `test`：Python 3.10 / 3.12 矩阵，`OPENAI_API_KEY: ""` 显式置空，跑全量 pytest。
Job 2 `claims`，逐条复验 README：
1. `run_eval --router rule` 输出必须含 `accuracy 83.3% (25/30)`（改 router 要连 README 一起改，这条红不是 bug 是过期声明）；
2. README demo 命令逐字复现（`import-csv` → `ask` → grep `ranks=128, threads=1` 与 `3.866`）；
3. report **字节确定性**：同库生成两次 `cmp`，再与仓库里提交的 `reports/scaling_1000000.md` `cmp`；
4. 无 key 时 `POST /ask router=llm` → **503**；非法 router → **422**（Pydantic 类型层拦截）。

### 2.7 其他模块要点

- **tracing**：一个 trace_id 串 5 个事件 `ask_start → route_result → tool_call → tool_result → answer`，JSON Lines 可回放；HTTP 侧 `"trace": true` 把事件放进响应而**不落盘**。
- **api.py**：纯协议翻译，零业务逻辑；缺 key 映射 503（依赖未就绪）而非 500；`/docs` 自动生成。
- **rag.py**：纯标准库 IDF 加权词法检索，命中作为**单独一条 system message** 注入；无命中不注入；已知局限：无相关性阈值（一个共享 token 就能命中）、检索效果**没有评测**（评测集打的是 tool call，不是解释质量）。
- **importer**：坏行显式抛错，不静默跳过；三个索引。
- **metrics**：没有单核基线就**不输出** speedup / efficiency，不用近似替代。
- **`mpi_like / hybrid_like`** 标签是从 `threads == 1 / > 1` 推断的，README 明写「不证明 OpenMP 在运行时真的激活」。

### 2.8 必须提前想好的诚实点

- `examples/sample.csv` 是 2026-06 `scaling_grid` 导出：**单节点、1M unknowns、36 行**，属 launcher 时代数据；`ask` 回答「128×1 最快、3.866 s」——与 `HPC_PETSC_Benchmark` 的 64×2 +13.1% 结论**相反**。
  答法：Agent 演示的是「让正确性可评测」的架构，数据集是早期单节点导出；把 408 个审计后 run 导入需要对齐列（nodes / 2D-3D / weak-strong）、工具加 `nodes` 参数、CI 断言 Agent 回答与 benchmark README 一致，且 30 问评测集要重出题重跑——这是明确的下一步，还没做。
- 仓库里有 `CLAUDE.md` / `AGENTS.md`：项目**用 Claude Code 辅助开发**。被问就正面答：spec-first（`SPEC.md` 先定边界与验收标准）、测试当合同（AI 不许改测试来通过）、所有公开声明由 CI 复验；架构决策（同构契约、不降级、lazy import、不用框架）是自己定的。
- 不用 LangChain / LangGraph 的理由：确定性工具 + 可评测路由是核心命题，框架会把「模型到底调了什么、参数从哪来」藏起来；只有两个工具、一层路由，框架的抽象没有收益。如果要 Planning / Memory / 多 Agent 才会引入。
- 为什么 SQLite：单文件、零运维、pytest 里可用临时库；数据 36 行。上线要换 Postgres 时只改 `db.py`（唯一 SQL 入口）。
- 未实现、只能说「了解」：Redis / 缓存、FAISS / 向量库、Docker、MCP、多 Agent。

### 2.9 「加一个工具」的扩展路径（面试官常问「如果要加个 worst_config 怎么改」）

`tools.py` 加纯函数（返回 `found` flag 的 dict）→ `db.py` 加查询 → `router.py` 词表 + 分支 → `llm_schema.py` 加 schema 与 `intent_from_tool_call` 映射 → `ask()` 加渲染分支 → `questions.jsonl` 加题 → `tests/` 逐层加合同 → 重跑两个 router 评测、更新 README 与 CI 的 83.3% 断言。

## 3. MARL_VALUE_FACTORISATION — 工程化部分

- `pyproject.toml`：`requires-python >=3.10,<3.12`，依赖全部上下界；`[tool.uv.index]` 指向 PyTorch CPU 源，**`uv.lock` 锁 CPU 版 torch**，无 GPU 可复现；`pytest` 配置 `pythonpath = ["src"]`。
- 测试三类：环境（矩阵博弈 payoff、episode 形状、Predator-Prey **seed 复现轨迹**、只暴露合作的 predator）；learner（三个 learner 各完成**一次 CPU 更新**）；注册表 / 配置（yaml 引用的 learner / env 都已注册）。

- 来源透明：`UPSTREAM.md` 只记录 PyMARL（**不写 ePyMARL**）；`results/legacy/` 与 `results/thesis/` 分开。
- 2026 整理时修的：Predator-Prey 合作边界；一条过期注释（写 `abs()` 保单调性，代码实际是 `softplus`）；中文注释译英。
